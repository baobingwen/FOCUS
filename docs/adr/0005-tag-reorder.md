# 0005: 标签自定义排列顺序 — 拖拽排序标签库

标签库当前按创建顺序（`id`）排列，常用标签会被新标签挤到后面。支持拖动改变标签库顺序，让高频标签稳定排在前面。

## Status

**accepted**

## Design

### 排序范围：仅标签选择器

自定义顺序只影响 **TagPicker 的芯片排列**（学习中 + 历史页编辑态共用同一组件，自动同步）：

| 界面 | 是否受影响 | 原因 |
|------|-----------|------|
| TagPicker 芯片（学习中 / 历史页编辑态） | ✅ 按自定义顺序 | 本功能核心价值：常用标签好找 |
| 今日概览「按标签」分组 | ❌ 仍按时长倒序 | 概览回答「时间花在哪」，时长信号更有信息量 |
| 历史页按标签筛选 | ❌ 筛选不看顺序 | 点选即筛，顺序无意义 |

### 数据模型

`tags` 表新增 `sort_order` 列（迁移 `003_add_tag_sort_order.sql`），与 `subjects` 表同款模式：

```sql
ALTER TABLE tags ADD COLUMN sort_order INTEGER NOT NULL DEFAULT 0;

-- 存量标签回填为创建顺序（id 越大越新）
UPDATE tags SET sort_order = id;
```

- `GET /tags` 改为 `ORDER BY sort_order, id`（`id` 兜底保证稳定序）。
- 新增标签沿用 subjects 的 `MAX(sort_order) + 1` 模式，自动排到末尾。
- 排序后 `sort_order` 是 0..N-1 的连续整数，由批量接口统一重编号，不做间隔。

### 后端 API

新增一个批量重排序接口：

| 接口 | 行为 |
|------|------|
| `PUT /tags/order` | body `{ ids: number[] }`；**全量**提交（缺一个 id 或集合与库中不一致 → 400）；事务内 `sort_order = 数组下标` 逐条重编号 |

- **为什么全量而非单条移动**：拖拽排序的提交点是「完成」按钮——一次结束时的快照，天然是整组数据；全量提交无顺移逻辑、事务原子、异常时无半新半旧中间态。单条 PATCH 的实时保存与「完成提交」的 UX 不匹配。
- 校验规则：`ids` 必须是纯数字数组；长度与标签总数一致；集合与库中 id 集合完全一致（缺一 / 多一 / 含不存在 id → 400）。
- 空标签库时 `ids: []` 合法（幂等无操作）。

### 前端交互

**入口**：TagPicker 行尾「+ 标签」之后加一个 ⚙ 排序按钮；标签数 < 2 时灰显（无需排序）。

**排序模式**（点 ⚙ 进入）：

| 行为 | 说明 |
|------|------|
| 芯片布局 | 保持横向 wrap 不变，每颗芯片左侧出现 ≡ 手柄 |
| 拖拽 | sortablejs 实现，`handle: '.drag-handle'` 限定手柄区才可拖（防点选误触），触屏/多行/自动滚动由库处理 |
| 点选禁用 | 排序模式下点击芯片不 toggle 选中（拖拽与点选的意图冲突） |
| 隐藏危险项 | 隐藏删除 × 和「+ 标签」，防拖拽时误删误增 |
| 完成 | 点「完成」→ 提交 `PUT /tags/order` → 成功后退出排序模式；提交失败 alert 并留在模式内 |
| 放弃 | 未点完成直接离开（如切走）即放弃，`allTags` 回滚到进入模式时的快照 |

**React 与 sortablejs 的同步**：sortablejs 在 `onUpdate`（`evt.oldIndex/newIndex`）时已把 DOM 节点移好；回调里只把 React state 数组重排成同样的新序——React 调和时发现 DOM 顺序与 state 一致，无操作不闪动。state 是唯一数据源，拖拽仅产生"新顺序"这一中间产物。

**为什么引入 sortablejs 而非自研**：wrap 多行跨行拖拽需处理占位符插入、自动滚动、触摸手势冲突，自研约 300+ 行且手机上难以测稳；sortablejs（~40KB）是触屏排序的事实标准。代价是前端引入第一个第三方 UI 库，但排序模式是其唯一使用面，收益（可靠 + 少代码）大于极简风格代价。

## Considered Alternatives

- **仅影响选择器 vs 也影响概览**：概览按时长倒序是「信息排序」（看时间流向），选择器按自定义序是「效率排序」（常用前置），两种排序目的不同，分开各自正确。统一成自定义序会丢掉时长信号。
- **长按直接拖拽（无模式开关）**：学习中芯片被高频点按，长按手势（300ms）容易误触；手机浏览器需处理长按的系统默认行为；无显式入口难被发现。模式开关让「点选」与「拖拽」在时间上互斥，误触成本为零。
- **单条移动 PATCH `/tags/:id`**：见上文「为什么全量」。
- **自研 Pointer Events 纵向列表**：零依赖且行序交换简单，但排序模式与平时形态差异大（wrap → 单列），且放弃了 wrap 原样拖的直接体验。
- **localStorage 仅本地**：顺序是全局标签库的属性，落库后手机/桌面/重装全一致；localStorage 换设备即失联，与全局库模型割裂。

## Consequences

- `tags` 表新增 `sort_order` 列（迁移 003），存量标签回填为 `id`，现有顺序不变。
- `GET /tags` 返回顺序变更（排序依据从 id 变为 sort_order），客户端无感（本来就按返回序渲染）。
- 服务端新增 `PUT /tags/order` 接口与全量校验逻辑。
- 客户端引入 sortablejs 依赖；TagPicker 增加排序模式（⚙ 入口、≡ 手柄、完成/放弃），学习中与历史编辑态共用。
- 版本号变更，v0.3.2（client 0.3.2 / server 0.3.1）。
