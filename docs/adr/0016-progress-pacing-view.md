# 0016: 学期配速视图（进度页）— 科目覆盖 + 各科配速

## 背景

用户 2026 年 9 月返校后，FOCUS 的使用形态从「暑假在家 · 台式机 · 每天连续 6 小时以上」变为「在校 · 手机 PWA 为主 · 碎片化」。实测数据（2026-07-06 ~ 2026-09-11，727 条记录）显示两次形态差异显著：

| 维度 | 暑假 7/6–8/31 | 学期 9/2–9/11 |
|------|---------------|---------------|
| 日均学习 | 中位数 6.56h，57 天连续无休 | 约 3.2h/有效天，10 天中 2 天完全空白 |
| 科目重心 | 数学 51.5% · 英语 26.6% · 专业课 16.7% | 英语 56% · 专业课 35% · **数学 7.6%（9 天仅 2.2h）** |
| 标签使用率 | 49.9% | 95% |
| 备注使用率 | 97% | 95% |

问题在于**现有界面无法让用户看见「哪一科正在被落下」**：今日概览是单日视角（`GET /api/records/today`），历史页只能按天翻看，两者都回答不了「数学多久没碰了」「这周的分配是不是偏了」。而学期里真正需要决策的正是分配问题——总量已由碎片化日程决定，可调的只有分配。

本次迭代新增第三个底部 tab「进度」，提供跨天的科目覆盖与配速回顾。

## 决策

以下 1–7 条为 `/grill-me` 逐条确认的设计点（问一问一），8–12 条为派生实现决策。

1. **入口：新增第三个底部 tab「进度」📈**。底部导航由 2 项变 3 项，与「计时 = 当下」「历史 = 某一天」并列，「进度 = 跨天回顾」。不放历史页（会稀释该页「单日」语义、手机上需滚动）、不放计时页（会稀释「专注计时」的极简定位）、不折叠进管理模式（看不见即失去提醒作用，与功能目的冲突）。

2. **范围：只做两块**——科目覆盖（断层）与各科配速（grill 时含「页头倒计时」共三块，用户实际观察后去掉倒计时，见第 9 条）。**不做**出勤/连续天数、页数趋势、标签（资料）维度：前两者与时长趋势信息重叠，后者会显著拉长页面且属另一条产品线（资料进度）。也**不在本页重复考研剩余天数**。

3. **统计窗口：滚动近 7 天（含今天），覆盖与配速共用**。自今天往回数 7 个自然日，按记录 `created_at` 的本地日期归属。不用自然周（周一起），避免周初窗口塌缩；不做 7/30 天切换，避免页面向 dashboard 倾斜。窗口外的断层由每行「上次学习距今 N 天」兜住。

4. **覆盖格判定：二元点亮，无时长阈值**。该科目当天存在学习记录即点亮。不设阈值——库里 5 分钟以下记录占 17.8%（最短 3 秒），一旦设阈值会把「背词 112 秒」这类真实碎片学习判成没碰；不误触误判的代价由配速模块的时长信息补偿。不用热力深浅：小格子上深浅差异有限，且条长已承载「多少」的信息。

5. **行集合：全部科目，按 `subjects.sort_order`**。不做「只显示近 30 天有记录的科目」——某科连续 30 天没碰就从页面消失，恰好把最该看见的断层藏起来；不做折叠，避免隐式规则与额外展开状态。

6. **配速口径：累计时长 + 占比条**，视觉与今日概览的科目条形图同款（用户授权「怎么直观怎么来」后确定）。条长 = 近 7 天该科累计时长相对最长科目的比例，条右侧显示累计时长。不加「日均」：条长表示总量而数字表示均值会造成口径不一致，反而不直观。

7. **数据来源：前端聚合 + 数据层新增区间查询**。新增 `recordsApi.range(from, to)`，服务端版经 `GET /api/records?from=&to=` 取记录、纯静态版经 IndexedDB 区间读取，两版返回形态一致（`{ records }`，含 tags），聚合逻辑（按日期 × 科目求和）在组件侧一套代码双版本共用。不在后端新增聚合接口：那会要求纯静态版在 IndexedDB 里复刻同一套聚合，重现 v0.5.3 统一导入校验所治的「双端两套实现」痛点。也不复用按日期接口连拉 7 次（7 个请求 + 7 份标签展开，即「日常点子」里已记录的 N+1 担忧）。**取数区间为「今天往前 89 天 ~ 今天」（90 天回溯窗口）**：展示窗口只需 7 天，但「上次学习距今 N 天」需要更早的历史，一次区间取数同时满足两者，避免二次请求。

8. **只统计已保存记录**：进度页不体现进行中的计时（in-progress 会话尚未落库）；结束学习保存成功后由 App 层 `refreshKey` 自增触发刷新。

9. **页头只放一行页面标题，不重复倒计时**（用户实际观察后调整）：右上角考研倒计时是 App 层常驻元素（三个 tab 都可见），本页再显示同一个天数属于同一信息的二次呈现，而进度页的职责是科目分配、倒计时并不参与这个判断。改为与另两个 tab 同款的页面标题「📈 学习进度」（计时页 `🎯 FOCUS` / 历史页 `📋 历史记录`），顺带解决两件事：三个页面标题风格一致；本页第一块内容不再顶到内容区 `pt-6`（24px）与右上角 `top-3`（12px）常驻倒计时的贴靠区。原方案曾为此抽 `utils/examDate.js` 共享常量，倒计时撤出本页后只剩 `ExamCountdown` 一个使用者，遂一并撤回该抽取（不留单消费者模块）。

10. **「上次」列口径**（表头「上次」；用户实际观察后补充——原方案只有一列裸数字，含义不直观）：该科目最近一条学习记录的本地日期与今天之差；今天学过显示「今天」，其余显示「N 天前」；**90 天回溯窗口内没有该科目的学习记录时显示「—」**（「从未学过」与「超过 90 天没学」不作区分——该窗口已覆盖本应用的完整历史）。

11. **双版本一致**：服务端版与纯静态版功能、界面完全一致，各自使用自己的数据层实现（与全项目既定原则一致）。

12. **只读视图，不进管理模式**：进度页不含任何修改/删除操作，因此不随 `adminMode` 变化，也不需要隐藏入口隔离。休息记录不参与覆盖与配速——休息不属于任何科目。

## 影响

- **数据层**：`utils/apiRest.js` 增 `recordsApi.range(from, to)`（`GET /api/records?from=&to=`）；`utils/apiLocal.js` 增同名方法（IndexedDB 区间读取 + 附 tags）。`utils/api.js` 分发入口无需改动（沿用既有 `recordsApi` 导出）。
- **服务端**：`routes/records.js` 的 `GET /` 在既有 `?date=` 之外支持 `?from=&to=`（同日含端点，`DATE(created_at) BETWEEN DATE(?) AND DATE(?)`，仍按 `created_at` 倒序并附 tags）；`?date=` 与无参行为不变。服务端版本号随之递增（0.3.7 → 0.3.8）。
- **客户端**：新增 `components/ProgressPage.jsx`（页头一行「📈 学习进度」标题；页内两常量：`WINDOW_DAYS = 7` 展示窗口、`LOOKBACK_DAYS = 90` 取数回溯窗口）；`App.jsx` 的 `TABS` 增第三项并把 `refreshKey` 传入。`ExamCountdown` 不改动（仍为右上角常驻倒计时 + 管理模式隐藏入口，是本项目考研剩余天数的唯一来源）。
- **测试**：服务端补 `?from=&to=` 区间查询用例（含边界日、跨月、与 `?date=` 行为不干扰）；客户端补 `apiRest`/`apiLocal` 的 `range` 用例与 `ProgressPage` 渲染用例（覆盖格点亮/距今天数/配速条比例/空状态）；`App.test.jsx` 补第三个 tab 的切换用例。用例计数同步 `TESTING.md`。
- **文档**：`CONTEXT.md` 增「进度页」「科目覆盖」「断层」「配速」「统计窗口」五个领域词与「进度查看流程」；`README.md` 增功能条目、结构树与流程说明；`CODE_STRUCTURE.md` 增组件职责；`ROADMAP.md` 记入已实现。
- **验收**：两版（`npm run dev` / `npm run dev:static`）均能看到第三个 tab 与正确数据；近 7 天无记录时显示空状态；全量测试全绿。

## 关联

- 相关概念见 CONTEXT.md「进度页」「科目覆盖」「断层」「配速」「统计窗口」。
